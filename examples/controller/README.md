# Controller

This example creates a Matter Controller using the ESP Matter data model.


See the [docs](https://docs.espressif.com/projects/esp-matter/en/latest/esp32/developing.html) for more information about building and flashing the firmware.

## 1. Additional Environment Setup

No additional setup is required.

### 1.1 Remote build with GitHub Actions

Push this repository, including the console changes, to GitHub. Under
**Actions**, select **Build Controller**, click **Run workflow**, select the
branch, ESP-IDF version, and the PSRAM mode matching your ESP32-S3 module.
The workflow uses ESP-IDF `v6.0.2` and octal PSRAM by default; quad PSRAM and
ESP-IDF `v5.5.5` are also selectable. No repository secrets are required.
In a fork, enable GitHub Actions first. For the initial manual launch, the
workflow must be present on the repository's default branch.

Once the run succeeds, download the `controller-esp32s3-...` artifact from the
run page. It includes the application, bootloader, partition table, ELF, and
flash arguments. The `controller-build-log-...` artifact contains the build log,
including when compilation fails. This workflow builds the Wi-Fi controller,
not the optional OTBR configuration.

Extract the firmware artifact, change into its `build` directory, and flash
with ESP-IDF's esptool environment (adjust the serial port):

```sh
esptool --chip esp32s3 --port <PORT> write-flash @flash_args
```

This uses the offsets generated by the build; do not flash the application
binary alone to address zero. To open the console with a configured ESP-IDF
environment, run `python -m esp_idf_monitor --port <PORT> controller.elf` from
the same directory. Use the configured console baud rate (115200 by default).

### 1.2 ESP32-C6 with 4 MB flash

Use the standalone C6 defaults instead of the base S3/PSRAM defaults:

```sh
idf.py -B build/esp32c6 -D SDKCONFIG="$PWD/build/esp32c6/sdkconfig" \
    -D SDKCONFIG_DEFAULTS=sdkconfig.defaults.esp32c6 set-target esp32c6 build
idf.py -B build/esp32c6 -p <PORT> flash monitor
```

This profile uses the native USB Serial/JTAG console, internal RAM, and a
4 MB partition table with a single application slot. BLE commissioning and
dual-slot OTA are not available. Connect both controller and device to Wi-Fi,
open the device's commissioning window, and use `pairing onnetwork` as below.
The GitHub workflow above currently builds only the ESP32-S3 profile.

## 2. Controller Example

See the [docs](https://docs.espressif.com/projects/esp-matter/en/latest/esp32/controller.html) for more information
about pairing and controlling an end-device using this example.

### 2.1 Wi-Fi control from esp_console

The default configuration enables the ESP-IDF console REPL on the configured
UART or USB console transport. Open it with `idf.py -p <PORT> monitor` after
flashing. The prompt appears after Matter and the commissioner are initialized.
Use `help`, `matter esp help`, or `matter esp controller help` to list commands.

The controller defaults also enable a test-only Telnet console on TCP port 23.
After Wi-Fi obtains an address, connect with `telnet <IP> 23`; USB remains
available. Use `matter esp terminal info` to print the address and port.
Telnet accepts the same `matter esp ...` commands and streams logs. It returns
`RESULT ESP_OK` or `RESULT ESP_ERR_...` followed by `matter>` for each nonempty
command. Asynchronous Matter operations may finish later; check their logs.
The server negotiates Telnet echo and echoes input; avoid duplicate local
echo. Enter starts a new output line and Backspace erases the previous
character. Empty lines redraw the prompt without a `RESULT`.
ESP-IDF level, timestamp, and tag prefixes are removed from Telnet output
for every module. `ROUTE_HOOK` messages are omitted from Telnet; USB retains
the original logs. For example:

```text
matter> matter esp terminal info
Telnet console: 192.168.1.194:23

RESULT ESP_OK
matter>
```

The address above is an example; DHCP may assign a different address.
Only one network session is served, with a 15-minute input idle timeout.
The C6 profile accepts up to 511 bytes per command; longer lines are rejected.
Do not run `wifi scan` over Telnet, as it disconnects Wi-Fi.

There is no TLS or authentication. Use only in an isolated test LAN, never
expose the port to the internet. This is a Matter console, not SSH or an OS
shell. Disable it with `CONFIG_ESP_MATTER_CONSOLE_NETWORK=n` or change its port
with `CONFIG_ESP_MATTER_CONSOLE_NETWORK_PORT`. To leave the Telnet client,
press `Ctrl+]`, then enter `quit`.
`Ctrl+C` and `Ctrl+D` close the session.
Telnet Interrupt Process also closes it. A client message saying
`Connection closed by foreign host` after Ctrl+C is expected.
This does not cancel a Matter operation already started.

Connect the controller to the same Wi-Fi network as the end-device and wait for
the IP address event before pairing:

```text
matter esp wifi connect "My Wi-Fi" "password"
```

With the ESP-IDF REPL backend, inspect the stored SSID, country/channel range,
DHCP client status, IPv4 address and gateway, or scan for access points:

```text
matter esp wifi status
matter esp wifi scan
```

The password is not printed. The scan briefly disconnects Wi-Fi, pauses
Matter's automatic reconnect, performs a passive scan, then restores the
previous station mode. Do not scan during commissioning or active device
control. A DHCP client that has not started yet and address `0.0.0.0` are
normal before association with an access point; the station uses DHCP.
The REPL connect handler uses Matter's Wi-Fi driver rather than restarting
Wi-Fi and initiating a competing connection attempt.

Diagnostics work over both USB and Telnet:

```text
matter esp diagnostics
matter esp diagnostics up-time
matter esp diagnostics mem-dump
```

`up-time` reports milliseconds since boot. `mem-dump` reports current free
memory, the largest free block, and the minimum free memory since boot,
in bytes, with `Internal` and `SPIRAM` columns. SPIRAM values are zero on
the C6 board without PSRAM. Telnet returns the data before `RESULT ESP_OK`.
These handlers use `ESP_LOGI`, as direct `printf` output is not captured by
the Telnet log hook. Keep INFO logging enabled for these command responses.

For a device already on that network, open its commissioning window, then pair
it with an unused node ID and its actual setup PIN:

```text
matter esp controller pairing onnetwork 1234 20202021
```

Alternatively, provision a new Wi-Fi device over BLE using its setup PIN and
discriminator:

```text
matter esp controller pairing ble-wifi 1234 "My Wi-Fi" "password" 20202021 3840
```

After commissioning succeeds, control the On/Off cluster (`6`) on endpoint `1`:

```text
matter esp controller invoke-cmd 1234 1 6 1
matter esp controller invoke-cmd 1234 1 6 0
matter esp controller invoke-cmd 1234 1 6 2
matter esp controller read-attr 1234 1 6 0
```

These commands turn the device on, off, toggle it, and read its OnOff attribute.
Replace the node ID and endpoint with those of your device. Being on the same
network alone does not grant control: the device must join this controller's
Matter fabric, or be added through a multi-admin commissioning window.
The console is accessible over serial/USB or Telnet. Matter commands reach
devices over the IP network, independently of the chosen console transport.

For an existing build, enable `CONFIG_ESP_MATTER_CONSOLE_USE_ESP_CONSOLE` in
`idf.py menuconfig` under `ESP Matter Console`. Keep `CONFIG_ENABLE_CHIP_SHELL`
and `CONFIG_ENABLE_WIFI_STATION` enabled, then rebuild and flash.

## 3. Controller in Rainmaker Fabric

Matter Controller in Rainmaker Fabric is available in [RainMaker Matter Examples](https://github.com/espressif/esp-rainmaker/tree/master/examples/matter).

Two different controller types are provided in RainMaker repository:

- [Matter Server-based Controller](https://github.com/espressif/esp-rainmaker/tree/master/examples/matter/matter_controller): The controller is set up with a Matter server instance. So it can be commissioned to Matter fabric with standard Matter commissioning flow. Then the NOC will be updated to controller's NOC during controller setting up.
- [Matter client-only Controller](https://github.com/espressif/esp-rainmaker/tree/master/examples/matter/client_only_matter_controller): The controller is a client-only Controller. It doesn't have standard Matter data model. And it uses RainMaker provisioning to join a Wi-Fi network.

## 4. OpenThread Border Router (OTBR) feature

### 4.1 Hardware Platform

See the [docs](https://github.com/espressif/esp-thread-br#hardware-platforms) for more information about the hardware platform.

### 4.2 Build

`sdkconfig.defaults.otbr` holds the OTBR-specific options and is layered on top of the base
`sdkconfig.defaults`. Build and flash the controller example with both:

```
idf.py -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.otbr" set-target esp32s3 build
idf.py -p <PORT> erase-flash flash monitor
```

*Notes*: The Thread Border Router DevKit Board uses USB port.

### 4.3 Pair and Control

- Connect the controller to Wi-Fi network with the device console

```
matter esp wifi connect {ssid} {password}
```

- Initializing a new Thread network dataset and commit it as the active one

```
matter esp ot_cli dataset init new
matter esp ot_cli dataset commit active
```

- Getting the operational dataset TLV-encoded string. The `<dataset_tlvs>` will be printed.

```
matter esp ot_cli dataset active -x
```

- Starting the Thread network

```
matter esp ot_cli ifconfig up
matter esp ot_cli thread start
```

- Pairing the Thread end-device

```
matter esp controller pairing ble-thread 1234 <dataset_tlvs> 20202021 3840
```

- Control the Thread end-device on the device console (On/Off cluster Toggle command)

```
matter esp controller invoke-cmd 1234 1 6 2
```

## A1 Appendix FAQs

### A1.0 Wi-Fi Connection Failed

The controller logs the Wi-Fi disconnect reason. `201` (`WIFI_REASON_NO_AP_FOUND`)
means failure before authentication and DHCP. Check `matter esp wifi status`
and `matter esp wifi scan`; ESP32-C6 supports only 2.4 GHz Wi-Fi.
If scanning finds no access points while another nearby device sees 2.4 GHz
networks, check the board's antenna, power supply and any antenna RF switch
against its manufacturer's documentation. RF-control GPIOs depend on the
board, not just the ESP32-C6 chip model.

### A1.1 Pairing Command Failed

I cannot finish the commissioning on the controller example:

-   For onnetwork pairing, please make sure that the end-device and the controller are on the same IP-network.
-   The controller uses the hard-code test PAA certificate by default so the PAI and DAC on the end-device should be generated by the [test cert](https://github.com/espressif/connectedhomeip/blob/4f7669b052b16bd054227376e1bbadac85419793/credentials/test/attestation/Chip-Test-PAA-NoVID-Cert.pem) and the [test key](https://github.com/espressif/connectedhomeip/blob/4f7669b052b16bd054227376e1bbadac85419793/credentials/test/attestation/Chip-Test-PAA-NoVID-Key.pem)
-   If you are still facing issues, reproduce the issue on the default example for the device and then raise an [issue](https://github.com/espressif/esp-matter/issues). Make sure to share these:
    -   The complete device logs for both the devices taken over UART.
    -   The esp-matter and esp-idf branch you are using.

### A1.2 Command Send Failed

I cannot send commands to the light from the controller:

-   Make sure the pairing command was a success.
-   The command data of cluster invoking command and attribute value data of attribute writing command should be a JSON string that matches the cluster description in Matter SPEC.
-   The CASESession will be lost on end-device after reboot. But the controller will still send commands on the previous CASESession. The controller will release previous CASESession after the last command is timeout. So the second command will re-establish a new CASESession in this situation.
-   If you are still facing issues, reproduce the issue on the default example for the device and then raise an [issue](https://github.com/espressif/esp-matter/issues). Make sure to share these:
    -   The complete device logs for both the devices taken over UART.
    -   The esp-matter and esp-idf branch you are using.

### A1.3 RAM optimization

The controller is RAM heavy, so `sdkconfig.defaults` puts the Wi-Fi/LWIP, NimBLE, Matter and mbedTLS allocations plus the BSS segments in PSRAM (`CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y`). The `esp_matter` and `esp_matter_controller` components move the `libCHIP.a` / `libesp_matter.a` / `libesp_matter_controller.a` BSS automatically; [`main/linker.lf`](./main/linker.lf) covers `libmain.a` and `libopenthread.a`.

-   `sdkconfig.defaults` uses octal PSRAM (`CONFIG_SPIRAM_MODE_OCT=y`). If the device crashes at startup with `PSRAM chip not found or not supported, or wrong PSRAM line mode`, set the mode that matches your module, e.g. `CONFIG_SPIRAM_MODE_QUAD=y` for a 2 MB quad-PSRAM part.
-   See [Configuration options to optimize RAM and Flash](https://docs.espressif.com/projects/esp-matter/en/latest/esp32/optimizations.html) for further options.
